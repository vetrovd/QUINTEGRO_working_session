# Домен — чистый редьюсер, UI не содержит логики переходов

Прототип существует, чтобы проверить корректность модели взаимодействия Family и Sitter, а не внешний
вид экранов. Поэтому все переходы живут в доменном модуле как чистые функции `(state, event) => state`
с guard-предикатами и производным расчётом денег, а компоненты только отправляют события и
спрашивают у домена, доступно ли действие. Часы — тоже зависимость домена, а не `Date.now()`.

## Considered Options

- **Логика в компонентах, состояние по месту**: быстрее на старте и привычнее для одноразового
  прототипа. Отвергнуто: тогда прототип не проверяет ничего, кроме вёрстки, — то есть не отвечает на
  вопрос, ради которого его строят.
- **Стейт-библиотека (zustand / xstate)**: xstate выразительнее для машин состояний, но добавляет
  собственный словарь поверх домена и делает тесты тестами библиотеки. Домен и без неё чистый, а
  `useReducer` покрывает потребность целиком.

## Consequences

- Недоступное действие проявляется как заблокированная кнопка с причиной из guard'а. Дырку в модели
  видно в интерфейсе, а не маскирует локальное состояние компонента — это и есть главный
  диагностический эффект прототипа.
- Тестовый шов один: домен. UI не тестируется вообще.
- Из прототипа выбрасывается только UI. Домен переносится в реальное приложение почти без изменений —
  он не знает ни про React, ни про браузер, ни про localStorage.
- Обратная сторона: любое изменение поведения требует нового события в домене, даже когда «достаточно
  локального стейта». Это сознательное трение; ослаблять его в компонентах нельзя, иначе решение
  теряет смысл.
